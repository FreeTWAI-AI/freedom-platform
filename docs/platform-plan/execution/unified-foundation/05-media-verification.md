# Bounded read-only media verification

`media:inventory` remains aggregate-only. `tsx scripts/media-verify.ts` computes actual source SHA-256 and byte sizes in bounded batches for the same seven fixed sources, including separate highlight image/thumb variants. It does not write, backfill, cut over, delete, back up, or restore data. MIME comes from the existing stored column or known writer; codec/image decoding is not run.

The default invocation validates a plan without opening a database or reading a connection environment variable. Supply all five explicit target flags: `--environment local|staging|public`, `--expected-database NAME`, `--schema NAME`, `--expected-role NAME`, and `--release-sha SHA`. Execution additionally requires `--execute-readonly` and `FREEDOM_MEDIA_DATABASE_URL`. Local targets require `fp_` database/schema names and a loopback host or explicit local Unix socket. Nonlocal target configuration requires `sslmode=verify-full`; no external target was used to validate this increment.

The role must exactly match, have SELECT access, and be neither superuser nor BYPASSRLS. Each query runs in an explicit read-only transaction. Ordinary tables without RLS are required; missing columns, views, foreign tables, RLS, and unavailable SELECT permission cannot produce a silently complete verification. Errors contain fixed safe codes, never connection strings or database/object diagnostics.

Defaults are 16 records, 64 MiB total bytes read, 10 seconds per SQL query, and 30 seconds per batch. Limits may be lowered or set up to 128 records, 64 MiB total, 30 seconds per query, and 60 seconds per batch. Every source row is capped at its fixed profile limit; video retains its actual 20 MiB limit and highlight thumbs retain their 200 KiB writer limit. Metadata is paginated before any byte SELECT, so oversized content is classified without fetching its bytes. Reads and fresh rechecks both count against the total budget. If a row cannot fit, the report stops with a cursor and an explicit limit reason; it never silently skips that row.

The cursor is a **scan position**, bound to target/environment/database/schema/role/release, registry fingerprint, and initial aggregate-inventory fingerprint. Encode its JSON as base64url for `--cursor`. A resumed batch opens fresh transactions, not the old PostgreSQL snapshot. `scanComplete` means the scan reached the last source; `contentVerificationScope: bounded_batch_only` and `pointInTimeSnapshot: false` remain explicit. Reports cannot establish that earlier pages remained unchanged after they were verified.

`--baseline-inventory` and `--baseline-records` accept base64url JSON evidence (bounded inputs; at most 128 baseline records). Aggregate drift is reported independently. Per-record baselines detect equal-size byte changes, source/pointer changes, and removed identifiers. Without prior per-record digests, equal-size changes between completed batches cannot be inferred from aggregate counts. A READ COMMITTED source reread detects committed changes during a row's verification, including a byte edit with no aggregate-version update. This is a fresh-statement observation, not a promise against edits committed after the last recheck.

Installed avatar, service-cover, banner, video, and the concrete migration102 social-thumbnail pointers are resolved through fixed typed tables. With a trusted server-supplied `ObjectStore`, verification performs a full GET and actual SHA-256 against the persisted immutable representation metadata. Without that port, asset verification is `not_run`/incomplete; it never falls back to retained SQL bytes or claims migrated content. Unknown future asset shapes fail incomplete until their concrete typed mapping is installed. The standalone CLI has no cloud credentials or implicit MEDIA binding and therefore cannot claim to verify installed objects by itself.

Reports may contain media identifiers, sizes, hashes, and anomaly/delta classifications. Treat them as private operator evidence. They contain no source bytes, object keys, URLs, credentials, or raw private diagnostics. Release identity is `operator_declared_not_runtime_verified`. Migration readiness remains `not_evaluated`, and restore remains `not_run` even after every bounded page passes.

Validation uses synthetic PostgreSQL with a separate low-privilege login and native local Miniflare R2 I/O. Preparation/hashing/tool execution occurs in Node; this is not an actual Worker handler, real Cloudflare memory/CPU quota, deployment, player, backfill, or restore proof. Full object verification still buffers a bounded 20 MiB object; future multipart/backfill adapters need their own memory budget.
