### 新庫搬移的實作要點

採用一致性 dump／restore 保留 IDs、關聯、序列、ACL 對應及 legacy media bytes，再套 canonical pending migrations。現有 candidate 已安裝 schema，**不是空白 restore 目的地**；不要把完整 dump 直接灌進已存在的同名 schema，也不要用無條件 `--clean` 解決衝突。需要新空目的地時，沿 Ted 已有的臨時 PG／新庫授權建立，再讓配置指向核對過的目標。

真正切換時排空背景／in-flight 寫入，使用最後一致性快照，不另造通用差異同步引擎。如果已有 R2 pointers，DB snapshot 與 object pins／備份要對應同一資料時點。新庫開始接收寫入後，舊庫就會落後；出問題採前向修復或一致性恢復，避免盲切舊庫造成新資料遺失。

現成入口：`scripts/database.ts` 匯出的 `migrate(pool)`；`deploy/cloudflare/sql/10-create-roles.psql`、`20-runtime-grants.psql`、`30-verify-readonly.psql`、`40-media-backfill-operator-grants.psql`；`packages/media-migration/restore-acl-lockdown.ts` 與 `scripts/media-restore-acl.ts`。順序是 restore → pending migrations → restore ACL lockdown → app grants／核對 → 專用 operator grants。`40-media-backfill-operator-grants.psql` 與 broker 的 40／45 scripts 用途不同。
