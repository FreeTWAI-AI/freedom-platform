## 規格層面已定、不需再問的事

以下是本目錄依計畫已定案方向做的設計選擇；若有更好的實作可以改，但不需要 Ted 逐項批准：

- 新交易用新的 order profile `hosted_checkout`，v1 預留不變（EC-SPEC-03 §3）。
- 庫存只有一份實體量 N；`reserved` 計數＝短期預留 H＋已付款未出貨配置 A，所以既有 `stock − reserved` 的讀者（含 `supplier-console/reads.ts`）不必改（EC-SPEC-03 §2）。
- 同一張訂單的 30 分鐘預留到期後不再重新預留；重新付款是從同一份 checkout 建立新訂單（EC-SPEC-03 §4）。
- 晚到的付款先記錄真實收款，再一次性重新配置全部行項；不足時進 `paid_unallocatable` 例外與退款待辦（EC-SPEC-03 §5）。
- 付款確認只來自驗證過的 server 通知或查詢；瀏覽器返回頁只觸發查詢（EC-SPEC-04 §4）。
- 綠界 profile 的每個凍結金額（單價、折扣後行項淨額、運費、總額）都是整數元；折扣以結算單位分攤，退款上限與發票／折讓品項也以整數元計算（EC-SPEC-04 §2、EC-SPEC-06 §2.5、§3.5）。
- 出貨者在結帳時就由貨在誰手上決定，履約單建立時寫入、不能改；C2 沒有人工指派、改派或換貨，做不到時只有改期或取消退款（EC-SPEC-05 §4.1、§4.5）。
- 代出貨同意撤銷只影響之後的結帳；已建立的履約單照凍結版本完成（EC-SPEC-05 §2.6）。
- 物流帳戶由伺服器依（出貨者商店、環境、服務）解析，出貨設定與命令都不帶帳戶參數（EC-SPEC-05 §2.3、EC-SPEC-04 §1.2）。
- 供貨對帳單依（付款方、收款方、幣別、付款天數）分張，每張只有一個到期日（EC-SPEC-06 §5.4）。
- 四個新能力 `commerce.hosted-checkout.v1`、`commerce.hosted-payment.v1`、`commerce.hosted-fulfilment.v1`、`commerce.hosted-invoice.v1` 各自跟所屬的 migration 一起登錄強制寫入下限；binary 先部署、migration 後套（EC-SPEC-10 §3）。
- 主機設定的布林只接受 `true`／`false`，Node、Worker、E2E 共用一個解析函式；不合規則或缺少依賴時整個服務就緒失敗，不部分啟用（EC-SPEC-10 §2.2）。
- 對外操作（付款交接、建單、開票、API 退款）先在 PostgreSQL 提交、寫進外部效果日誌，才呼叫綠界；還原後一律先進隔離模式，對帳完成才解除（EC-SPEC-10 §8.2～§8.5）。
- 留下的摘要不能用來比對猜測的個資：聯絡摘要含隨機 salt，salt 隨遮罩清除；建立 checkout 的請求摘要以冪等鍵做 HMAC，鍵本身不保存（EC-SPEC-09 §3）。
- 交易信件的佇列不存個資，寄出時才讀收件人；資料遮罩後尚未寄出的信不再寄（EC-SPEC-10 §6.3）。
- commerce 的排程工作排在 GitHub 同步之前；每次最多 200 列、50 次對外呼叫、5 分鐘，數值以 staging 觀察校準（EC-SPEC-10 §5）。
- provider 通知在驗證簽章之前的限流以（帳戶, 網路）為鍵，不只以帳戶為鍵：`account_ref` 印在每張付款交接表單上，只以帳戶為鍵時任何人都能讓真通知收到 429（EC-SPEC-09 §4、EC-SPEC-04 §9）。
- 同一 attempt 的付款事件依收到的順序套用；隔離解除後先套用延後的事件，再釋放到期預留，有尚未套用的已驗證付款的訂單不釋放（EC-SPEC-04 §5.4、EC-SPEC-03 §5.2、EC-SPEC-10 §8.3）。
