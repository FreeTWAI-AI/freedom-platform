# EC-SPEC-01 產品與視覺：角色、動線、狀態、手機與可存取性

狀態：proposed（2026-10-15），基準 `efaf314d`。對應需求 EC-R01、R07、R08、R11、R21、R45、R58；驗收 EC-AT01、03、04、06、10、18、49、51、65、66（全部 `not_run`）。逐頁的操作／API／權限在 [pages.md](pages.md)；本文件定共同規則，資料契約在 EC-SPEC-02～06。

## 1. 角色

| 角色 | 身分來源 | 看得到 | 不能做 |
| --- | --- | --- | --- |
| 訪客 | 無 | 已發布的店面、商品、政策頁（B01–B03、B09）；購物車與結帳準備（B04、B05） | 讀任何訂單、草稿或預覽 |
| 顧客（guest） | 結帳建立的店家顧客記錄＋該訂單的私有存取憑證（EC-SPEC-02 §4） | 自己的訂單、付款、包裹、發票、售後（B06–B08）；遺失憑證時走 B10 | 用訂單編號或 Email 直接讀單；被要求加入公會或註冊 |
| 會員顧客 | 工坊會員 session；顧客記錄可選擇連結會員 | 同上，另有跨店「我的訂單」 | 因為是會員就看到別人的單 |
| 店主 | 事業 owner | 自己店的 E01–E11 | 看別家店的顧客或訂單；讀出收款金鑰 |
| 店員 | 事業成員＋被授予的能力（提議清單見 EC-SPEC-09 §2） | 依能力裁切的 E 頁 | 超出能力的命令；伺服器拒絕，不只隱藏按鈕 |
| 供應商 | 供應商事業成員（Supplier Console） | 出貨者是自己事業的履約任務（建立履約單時依代出貨同意自動指派，EC-SPEC-05 §4.1）與最小收件資料（SL-01–05） | 讀整張零售訂單、付款資料、其他供應商的包裹 |
| 平台管理員 | Access＋平台管理身分 | 既有 admin 服務與稽核 | 本案不新增管理員瀏覽顧客個資的頁面；不代商家收款 |
| Agent／技能／MCP | 委派憑證（不是使用者本人的瀏覽器 session） | 委派範圍內、且不在右欄的 API，照樣經過能力檢查 | 成為授權來源；略過確認步驟（EC-SPEC-07）。C2 的委派憑證**一律不能**做以下事情，任何委派範圍都打不開：讀收件或聯絡資料、開標籤列印、建立或作廢託運單、核准或送出退款、取消已付款的訂單或行項、作廢發票或開折讓、修改寄件地／出貨設定／物流與收款與發票帳戶／代出貨同意／政策。這些只能由有該能力的成員在自己的 session 操作（Supplier v1.1 §2.2、SC-LAT01；decisions.md）。Agent 可以讀不含個資的清單與狀態、準備草稿，由成員確認後送出 |

## 2. 旅程與頁面

| 旅程 | 頁面順序 | 伺服器動作 | 里程碑 | 驗收 |
| --- | --- | --- | --- | --- |
| J01 開店與發布 | E01 → E03 → E04 → 預覽 → 發布 → B01 | launch plan／installation（既有）、appearance、products、publish | C1 | AT03、AT06 |
| J02 購物與結帳 | B01／B02 → B03 → B04 → B05 | cart-quotes → checkouts → orders | C1 準備、C2 送出 | AT04、AT10、AT12 |
| J03 付款成功 | B05 → 付款交接頁 → provider → B06 → B07 | 建立 attempt；只認 server callback／查詢 | C2 | AT18 |
| J04 付款失敗或未知 | B06 → 查詢 → 續付或回到 checkout | 前一 attempt 確定沒有付款（失敗，或當場查詢顯示未付）才建新 attempt；結果不明不建（EC-SPEC-04 §4.3） | C2 | AT18、AT20 |
| J05 賣家自出貨 | E05 → E06 | fulfilment order、shipment、交寄證據 | C2 | AT38、AT39 |
| J06 供應商代出貨 | E05 → E06（已自動指派給供應商）→ SL-02 → SL-03 → B07 | 付款後依代出貨同意建立履約單（出貨者＝供應商）、接受、最小收件資料、shipment | C2 | AT11、AT43 |
| J07 多來源拆包 | B05 顯示包裹與運費 → E06／SL | 結帳前算出配送群組並凍結 | C2 | AT10、AT34 |
| J08 取消／退貨／退款 | B07 → B08 → E05／E09 → SL-04 | cancel、return request、refund、檢驗回庫 | C2 | AT22、AT42 |
| J09 發票 | B05 發票欄 → E10 → B07 | issue／void／allowance | C2 | AT45–47 |
| J10 技能書與下載 | E01 三個入口 | 技能書／應用／可攜發行物的關係 | C1（下載 C3） | AT52、AT53 |
| J11 獨立營業 | 可攜包的本機管理頁（EC-SPEC-08） | 同 J01–J09 適用部分 | C3 | AT55、AT56 |
| J12 部分外移 | E11 → 遷移工具 | 唯一寫入權威、在途 callback | C3 | AT59、AT60 |

C1 的 B05 是「結帳準備」：訪客不用登入、不用入會就能填到最後一步（AT04）。店家尚未開通收款時，最後一步顯示「這間店尚未開放線上付款，訂單無法送出」，購物車保留，不出現任何像是可付款的按鈕（計畫 §5 C1）。

## 3. 買家頁的位置與網址

B 頁是 `/shops/:slug` 之下的獨立文件，不進 portal 的 `app-frame`（原因見 pages.md「共同前提」）。

| 頁面 | 網址（提議） | 產生方式 |
| --- | --- | --- |
| B01 店首頁 | `/shops/:slug`（既有） | server HTML |
| B02 商品清單／搜尋 | `/shops/:slug/products?q=&category=&sort=&page=` | server HTML；條件全在 query string，可分享、可重新整理 |
| B03 商品詳情 | `/shops/:slug/products/:sku`（既有）；變體選擇的表示法見 EC-SPEC-02 §1 | server HTML＋加入購物車的小程式 |
| B04 購物車 | `/shops/:slug/cart` | 店面 client bundle |
| B05 結帳 | `/shops/:slug/checkout`，步驟反映在 history state | 同上；與 B04 同一份 bundle，切換不遺失記憶體內的草稿 |
| 付款交接頁 | `/pay/ecpay/{handoff_token}`（EC-SPEC-04 §4.1：一次性 token、15 分鐘到期；固定前綴讓 CSP 的 `form-action` 例外只對這個路徑） | server HTML；provider 表單在這頁送出 |
| B06 付款返回 | `/shops/:slug/payment-return/:attempt_ref`，只用 GET | server HTML＋輪詢查詢 |
| B07／B08 訂單 | `/shops/:slug/orders/:order_ref`；退貨申請 `…/return` | 店面 client bundle |
| B09 品牌與政策 | `/shops/:slug/about`、`/shops/:slug/policies/:kind` | server HTML |
| B10 找回訂單 | `/shops/:slug/order-access` | server HTML 表單 |
| 會員「我的訂單」 | portal 既有 `#reservations` 頁上方新增「訂單」區塊（flag 開啟時）；點擊進入 B07 | v1 區塊的標題、角色名稱與數量不變（`hosted-order.spec.ts`） |

規則：

- 付款返回網址與交給 provider 的任何網址都**不含**訂單存取憑證，頁面也不顯示個資；只顯示這次付款的狀態與「查看訂單」按鈕（這個瀏覽器有憑證或會員登入才打得開，否則導到 B10）。
- 信件裡的訂單連結（需要寄送授權，EC-SPEC-02 §4）打開後，憑證換成這個瀏覽器的私有憑證，網址列不留憑證。
- 店家未開通新結帳時，B01／B03 保留 v1 的文案與連結（「登入確認預留條件」「登入查看預留狀態」「查詢我的預留」），既有 `storefront-product.spec.ts`、`hosted-store.spec.ts` 的斷言不變。開通後換成「加入購物車」。
- `script-src 'self'`：店面互動只能用外部 bundle，不寫 inline script。`form-action 'self'`（`platform-app.ts:147`）：只有付款交接頁的 CSP 加上該 provider profile 的固定網域（EC-SPEC-04）。

## 4. 店面視覺系統

### 4.1 基底

沿用 `apps/portal-web/public/shops.css` 的明亮基底，不另建色盤（DESIGN.md「新增頁面先沿用這裡的 token」）：頁面 `#f6f8fb`、卡片白、正文 `#1c2636`、輔文 `#566376`、邊界 `#dce3eb`、主行動萊姆綠 `#c4ff20` 配深字、焦點外框 3px `#537300`。系統字型、正文至少 14px、表單在手機 16px、行高 1.6 以上、觸控至少 44px、價格用等寬數字。

新增樣式都以 `shop-` 為前綴，只由店面文件載入；店面 bundle 不載入 portal 的 `rpg-theme.css`、`light-theme.css` 或主題切換。B 頁固定明亮配色（`color-scheme: light`），不跟隨會員在 portal 選的主題。

### 4.2 店家可調整的範圍（E03）

只有受控參數，沒有自訂 CSS、HTML 或 script：

| 參數 | 範圍 | 約束 |
| --- | --- | --- |
| 主色 | 8 組預先挑選的主色（含預設萊姆綠） | 每組按鈕字與底色對比 ≥ 4.5:1、與頁面底色 ≥ 3:1，以單元測試計算 WCAG 對比 |
| 封面 | 一張店家上傳的封面圖（新 asset 用途，EC-SPEC-02 §2） | 沒有封面時不拿第一張商品照硬撐首屏，改用店名與介紹的文字版首屏 |
| 店標 | 選填的方形店標 | 沒有就只顯示店名文字 |
| 版型 | 既有 `catalog-grid-v1`／`catalog-list-v1`，加主打商品（最多 8 件）與分類入口兩個區段開關 | 版型只改排列，不改語意 |
| 公告列 | 選填一行，最多 80 字 | 不跑馬燈、不自動輪播 |

### 4.3 頁首與署名

商家品牌在前：頁首左側是店標／店名，右側是搜尋與購物車（含件數）。自由工坊改為頁尾署名「使用自由工坊開店」，附原始品牌圖（不重畫、不裁字標、維持比例）連回首頁。店面頁不顯示會員區的全域導覽、聊天泡泡或新手導覽角色。

### 4.4 商品呈現

- 照片 1:1 `object-fit: contain`；沒有照片顯示既有「尚未提供商品照片」；圖片載入失敗顯示同一個佔位與商品名，不留破圖。首屏第一張 `loading="eager"`，其餘 lazy。
- 只顯示真實資料：沒有評價、售出數、倒數庫存、「熱賣」「限量」字樣，除非來自可查證的資料（計畫 §7.2）。可售狀態只分「可購買」「目前沒有可售數量」「已下架」。
- 價格由 server 以整數最小單位格式化（100 minor＝1 TWD，`format.ts`），畫面不自行換算；折扣顯示原價與折後價，兩者都來自同一次 quote。

## 6. 狀態與文案

### 6.1 共同模式

| 情況 | 呈現 | 不做 |
| --- | --- | --- |
| 讀取中 | 保留版面骨架與標題；按鈕顯示進行中並停用 | 整頁轉圈遮住已有內容 |
| 讀取失敗 | 「無法取得…，請稍後重試」＋重試；保留已顯示的資料並標示時間 | 顯示 0 件、0 元或空清單 |
| 空資料 | 說明為何是空的＋一個可用的下一步（例如清除篩選） | 只有「沒有資料」 |
| 欄位錯誤 | 欄位旁文字＋`aria-invalid`／`aria-describedby`；送出時頂部錯誤摘要可點到欄位；保留輸入 | alert、整頁重置 |
| 寫入回應遺失 | 「正在確認結果」；用原 Idempotency-Key 與原內容重試或查詢；結果確認前不允許改內容 | 換新 key 重送；顯示失敗卻其實成功 |
| 權限不足 | 「你沒有這個操作的權限」＋誰可以處理 | 隱藏後讓人以為功能不存在 |
| 服務暫停 | 指出是哪個服務（付款、物流、發票）與影響範圍 | 籠統「系統錯誤」 |

### 6.2 付款（B06、付款交接頁）

| 狀態 | 買家看到 | 可用操作 |
| --- | --- | --- |
| 尚未付款 | 「請在 {時間} 前完成付款，逾時保留的商品會釋出」；保留已過期時改為「付款期限已過，保留的商品已釋出」 | 前往付款；取消訂單；保留已過期時只有回到商店 |
| 付款確認中 | 「已回到商店，正在向付款服務確認結果」；自動查詢一段時間（次數有上限），之後改為手動 | 重新查詢；稍後再看（訂單連結） |
| 已前往付款，還沒有結果 | 標籤同「付款確認中」：「還沒收到這次付款的結果」；可以重新付款時另加「如果你沒有完成付款，可以重新付款；我們會先向付款服務確認，不會重複扣款」 | 查詢付款結果；重新付款（伺服器先查詢，確定沒有付款才建立新的付款，EC-SPEC-04 §4.3） |
| 已付款 | 「已收到付款」；後續進度在訂單頁（付款後缺貨由庫存軸說明，§6.3） | 查看訂單 |
| 付款金額待店家確認 | 「我們收到的付款和這筆訂單不符，店家會確認並處理退款。請不要再付款。」 | 查看訂單（B06）；不提供付款、重新付款或查詢 |
| 已退款 | 「店家已登記退回這筆訂單收到的全部款項。入帳時間依發卡銀行而定，沒有收到時請聯絡店家。」M2 只有店家的人工紀錄，平台沒有向綠界確認，所以寫「已登記」；只在不符訂單的付款退完、又沒有確認付款時出現（EC-SPEC-03 §3.2） | 查看訂單；不提供付款、重新付款或查詢 |
| 付款未完成 | 「這次付款沒有完成，沒有扣款」 | 重新付款（同一訂單、保留仍有效時）；保留已結束則回到 checkout 重新確認價格與庫存（EC-SPEC-03 §4.3） |
| 結果不明 | 「暫時無法確認這次付款的結果，請不要重複付款」；查詢或重新付款得到 `payment_result_pending` 時顯示 | 重新查詢（`Retry-After` 之後）；聯絡店家（訂單對話上線後，B08）；這段時間不顯示重新付款 |

畫面依訂單 DTO 的 `payment_state`、`latest_payment_attempt` 與 `can_resume_payment` 決定，依序取第一個成立的：`overpaid` → 付款金額待店家確認；已確認付款 → 已付款；`refunded` → 已退款；`pending` → 付款確認中；訂單已取消 → 不再提供付款；attempt `paid` → 付款確認中；`awaiting_result` → 已前往付款，還沒有結果；保留已過期 → 付款期限已過；`failed`／`expired` → 付款未完成；其他 → 尚未付款。`simulated` 對買家照未付款顯示，不提模擬（§6.3）。「前往付款」與「重新付款」只在 `can_resume_payment` 為真時出現，頁面不自己判斷能不能付款。

返回頁永遠先查 server 狀態；網址或 provider 帶回的欄位不改變顯示（EC-AT18）。返回頁只顯示狀態、訂單編號與店名，不顯示聯絡資料、商品或金額；這個瀏覽器沒有這筆訂單的權限時，連到 B10。交接頁在載入後自動送出一次。一定要有可見、可用鍵盤的「前往綠界付款」按鈕：沒有 script 時立即顯示；有 script 時停留 10 秒後才顯示，按一次就停用（EC-SPEC-04 §4.1）。送出後按上一頁回到交接頁，不重送表單，顯示「已前往付款頁。要重新付款，請回到訂單頁。」與「返回訂單」。

### 6.3 各軸線的文字

訂單畫面不用一個「已付款」代表全部完成（計畫 §9.1）。下表是買家與賣家看到的文字。包裹的文字只有一個來源：EC-SPEC-05 §5.1 的對照表，「買家看到」給買家，「出貨者看到」給賣家的 E06 與 Supplier Console 的 SL 頁，所以賣家與供應商看到同樣的包裹進度（J06）。履約單的文字在下表的「履約」列；SL-02 的分頁名稱在 EC-SPEC-05 §4.2。

| 軸線 | 內部值（EC-SPEC-03～06） | 買家 | 賣家 |
| --- | --- | --- | --- |
| 訂單 | `open`／`cancelled`／`closed` | 進行中／已取消（原因）／已完成 | 同左 |
| 付款 | `unpaid` | 尚未付款 | 待付款 |
|  | `pending` | 付款確認中 | 付款確認中 |
|  | `paid` | 已付款 | 已收款 |
|  | `partially_refunded`／`refunded` | 已部分退款／已退款 | 同左 |
|  | `overpaid` | 付款金額待店家確認 | 收款與訂單不符，需處理 |
|  | `simulated` | 不顯示（只在測試環境） | 模擬付款（不會出貨） |
| 庫存 | `held` | 已為你保留到 {時間} | 保留中 |
|  | `unallocated` | 已付款，店家確認庫存中 | 已收款但缺貨，需處理 |
|  | 其他 | 不顯示 | 已配貨、部分出貨、已出貨、已釋出 |
| 履約 | `awaiting_acceptance`／`accepted`／`unable_reported`／`fulfilled`／`cancelled`（EC-SPEC-05 §4.2） | 不顯示（買家只看包裹） | 待供應商接受（自出貨不會出現）／備貨中／供應商無法履約（原因）；同意等候時「等候至 {日期}」／已全部交寄／已取消 |
| 包裹 | EC-SPEC-05 §5.1 | 該表「買家看到」欄；有未結例外時另顯示「配送異常」 | 該表「出貨者看到」欄 |
| 發票 | （EC-SPEC-06 §3） | 開立中／已開立／已作廢／已折讓／折讓待你在 Email 確認；店家不開立時顯示店家的說明 | 另有「開立失敗，需處理」「結果確認中」「待更正」 |
| 售後 | （EC-SPEC-06 §2.3） | 申請中／未同意（原因）／已撤回／已同意，請寄回（地址與期限）／已收到退貨，檢驗中／退款處理中／已完成 | 同左；未完成時列出卡住的軸（實物、錢、發票） |

「已建立託運單」不等於「已交寄」（EC-AT39）；退款完成不等於商品已回庫（計畫 §11.4）。顯示用訂單編號短且好唸，但不能拿來讀單（EC-SPEC-02 §4）。

## 7. 主要頁面的互動

### 7.1 B03 → B04：加入購物車

- 「加入購物車」把 SKU、數量、店面發布版本存在瀏覽器（每店一份，最多 50 行、每行最多 99，與現有行項上限一致），不存價格當依據、不存個資。
- 加入後開啟購物車側欄（dialog：標題、關閉按鈕、Esc、焦點返回「加入購物車」）；手機為全寬底部面板。件數變化以 `aria-live="polite"` 宣告。
- 多個分頁之間以 storage 事件同步件數。

### 7.2 B04 購物車

- 每次載入與修改後向 server 取 quote（有防抖），逐行顯示單價、可售狀態、小計；價格與加入時不同時標示「價格已更新」。
- 數量不足或下架的行：提供「改為可購買數量」或「移除」，處理完才能前往結帳。
- 摘要：商品小計、折扣、運費（「於下一步依配送方式計算」，不顯示 0）、總額。

### 7.3 B05 結帳

| 步驟 | 欄位 | 規則 |
| --- | --- | --- |
| 1 收件與配送 | Email、手機、姓名；宅配（縣市、鄉鎮市區選單→郵遞區號自動帶入、地址）或超商取貨（開啟 provider 門市地圖，返回後顯示門市名稱與地址，可更換） | 從門市地圖返回時焦點回到門市欄並宣告所選門市（EC-AT66） |
| 2 包裹與運費 | 每個包裹的商品、預計出貨時間、運費；不可配送的商品在這一步說明並給替代方式或移除 | 不在付款後才說不能寄（EC-AT12） |
| 3 付款與發票 | C2 首發付款方式（DC02），加上店家提供的銀行匯款與面交付款（EC-SPEC-11 §6.1）；發票類型依店家設定（會員載具、手機條碼、自然人憑證、捐贈、公司統編，EC-SPEC-06 §3.3）；店家不開立時只顯示店家的說明 | 依所選類型驗證，切換類型清空不適用的欄位（EC-AT45）；條碼、捐贈碼與統編的線上查詢只提示、不阻擋 |
| 4 確認 | 商品、折扣、每個包裹的運費、總額；店家政策連結與必要同意 | 「確認並付款」只有店家已開通收款時出現（§2）；選線下付款時按鈕是「確認下單」，下單後直接到 B07 |

- 每一步推入 history state，瀏覽器上一頁回到前一步。進入新步驟時焦點移到該步驟標題；步驟列用 `<ol>` 與 `aria-current="step"`。
- 草稿：存在這個分頁的 sessionStorage，下單成功、按「清除」或 30 分鐘未操作即刪除；不用 localStorage、不送分析。
- 「確認並付款」：依序建立 checkout、訂單（各帶 Idempotency-Key），成功後進付款交接頁。回應遺失時以同樣的 key 重試，server 回同一筆結果（EC-AT51）。
- 草稿與未完成的命令綁定原本的身分（guest 或某位會員）與店家；登入身分改變後不再送出舊草稿，顯示「登入身分已變更，請重新確認」（EC-AT49）。

### 7.4 B07 訂單

頁首：顯示用編號、下單時間、店名、訂單狀態。下面依序是「需要你處理」（例如付款期限）、付款、包裹（每個包裹一張卡：商品、物流、追蹤碼、事件時間線）、發票、售後。收件資料只在這頁出現。操作只出現合法的：取消（未付款；已付款未出貨時是申請取消）、申請退貨或退款（期限內）、聯絡店家（訂單對話，EC-SPEC-06 §2.1）。

### 7.5 Seller Console（E 頁）

殼由 Supplier Console 提供（SC-SPEC-01：桌面 12rem 側欄、窄螢幕 `<select>`、頁名 h1 由 `App.tsx:830` 工具列提供；`HostedStore()` 路由分派與離頁保護由該工作階段負責）。Commerce 提供以下項目：

路徑是 `#stores/<tenant>/<instance>/<slug>`（店的根目錄）；供應商頁面在 `…/supply/…`（SC-SPEC-07 §2）。這組 slug 是 2026-10-15 與 Supplier Console 工作階段約定的清單。賣家主控台的開關關閉時，這些 slug 回到既有的商店頁，`orders/<order_id>` 回到訂單清單；`orders` 保留 `sellerOrdersRoute` 既有的 4 段路徑行為。不認得的 query key 一律忽略；不用 `replaceState`；ID 以 `OpaqueId` 檢查。

## 8. 可存取性與鍵盤

- 每頁一個 h1；店面頁有「跳到主要內容」；地標 `header`／`nav`／`main`／`footer`。`lang="zh-Hant"`。
- 所有圖示按鈕有可存取名稱（「從購物車移除 {商品}」「增加 {商品} 數量」）；數量欄是可輸入的數字欄位，旁邊的加減按鈕不是唯一方式。
- 狀態不只靠顏色：徽章有文字，必要時加形狀圖示。
- dialog／側欄：標題、可見關閉、Esc、焦點鎖定與返回。
- 鍵盤可完成：搜尋、篩選、加入購物車、改數量、選配送與門市、前往付款、查詢付款結果、申請退貨；賣家可完成：開啟訂單、處理無法履約回報、建立包裹、列印、標記交寄。
- 尊重 reduced-motion；沒有自動輪播；觸控 44px；所有 hover 有 focus-visible 對應。

## 9. 視覺驗收

真瀏覽器、隔離資料，五個寬度：1440／1280／768／390／320 CSS px（EC-AT65）。只檢查元素存在不算通過。

| 頁面 | 至少要拍的狀態 |
| --- | --- |
| B01 | 有封面、無封面、無商品、長店名 |
| B02 | 有結果、無結果、篩選中 |
| B03 | 有變體、售完、圖片失效、長商品名、v1 預留模式 |
| B04 | 多行、價格更新、數量不足 |
| B05 | 每一步、欄位錯誤、選好門市、兩個包裹、店家尚未開通收款 |
| B06 | 確認中、已付款、未完成、結果不明 |
| B07 | 部分出貨（一包已到、一包未出，EC-AT34）、退貨中 |
| B09、B10 | 一般、送出後 |
| E02、E05、E06、E03 預覽 | 明亮、夜航、敘生三個主題；有資料、空、讀取失敗 |

每次量測：

- `document.documentElement.scrollWidth` 不超過視窗寬度（320px 不得橫向捲動）。
- 每個 `.btn`／`.shop-button` 的寬高：主要按鈕不被拉成全寬（portal `.stack` 會把裸按鈕撐滿，需包在 `.actions` 裡），觸控高度 ≥ 44px。
- 徽章與按鈕取 computed color 比對，明亮主題的全域 `.badge` 規則會蓋過模組顏色。
- 切換主題後等 0.16s 過場結束再拍，避免把過場灰色誤判為對比問題。
- E 頁右下角聊天泡泡不得蓋住主要操作。
- 只用鍵盤走完 §8 的流程並記錄焦點位置（EC-AT66）。
