# Closed avatar maintenance and reference capture

[maintenance.ts](maintenance.ts) and additive [082](../../migrations/082_asset_maintenance.sql) provide internal deletion fencing and backup **reference capture**, not a scheduler, public/member API, completed backup, restore tool or permission to delete production objects. No cloud binding or credentials are discovered. The module is disabled unless its caller explicitly opts in **and** the DB maintenance policy is enabled and fully configured. Tests use a disposable `fp_*` schema and synthetic fake-store bytes.

## Policy and activation

The migration inserts a disabled policy row with no retention/lease/pin defaults. Configuration must explicitly supply revision, orphan and retired retention, bounded delete lease, capture deadline, pin deadline and maximum reference count. The approved starting retention values are at least 48 hours for uncommitted/unreferenced objects and seven days for replaced versions; these are tested configuration, not enabled production defaults. User-facing removal must become unreadable immediately through the domain bridge independently of physical retention.

All referenced pointers, including a stale legacy/prototype pointer, block collection. A non-finalized intent whose immutable deadline remains live also blocks collection, even when its current worker lease expired. Only unreferenced `pending/rejected` assets past orphan retention and `retired` assets past replacement retention are eligible. Unreferenced `ready` is conservatively not collected. No quota is released based on a storage 404 or deletion observation: a late PUT may still consume bytes.

The operations caller owns environment/DB/bucket identity checks and authority. These library functions are not machine credentials or member authorization. Arbitrary privileged DDL/TRUNCATE is outside their threat model. No new HTTP, queue, cron, MCP or native entrypoint is registered. No normal app port should enable R2 deletion; [the native adapter](../../packages/asset-storage/README.md) defaults deletion off separately.

## Deletion protocol and lock order

`claimDelete(assetId)` reads immutable owner identity, then locks real avatar → typed pointer → upload intent → asset → maintenance gate → tombstone. It never holds the gate while waiting for a business row. The database independently repeats eligibility checks, including capture barriers and pins. A successful claim inserts a permanent tombstone and changes `assets.deletion_fence` from 0 to 1 in the same transaction. The original 079 states, immutable identities, representation metadata and constraints remain unchanged; deletion is not represented by falsely rewriting an asset to `ready` or erasing history.

The asset tuple change matters: a locking READ COMMITTED reader observes the fence; an old REPEATABLE READ/Serializable snapshot fails serialization instead of consulting an invisible side-table tombstone. SQL guards lock the asset before rejecting ready transitions, pointer attachment, representation insertion and intent mutation. The fence and tombstone cannot be removed or reset. Direct SQL still cannot turn a fenced asset into an attachable one.

`deleteObject({assetId,attempt,leaseToken})` resolves the exact key from immutable database identity, validates the current bounded lease, commits, then calls DELETE and HEAD outside every SQL transaction. No arbitrary raw key is accepted. It finally records a fenced observation in PostgreSQL. Results are `missing`, `present` or `unknown`, never a permanent-deletion/erasure certificate. Adapter errors are not stored or surfaced with object keys, credentials or bytes.

After a successful observation the lease is shortened to the current clock so an explicit rescan can claim the next monotonically increasing attempt. Active lease takeover is rejected; expired attempts cannot overwrite newer evidence. A crash or PG failure after DELETE keeps the permanent fence and can retry the same current lease, or claim a new attempt after expiry. A delayed old PUT can recreate the exact key even after a `missing` observation; future explicit same-key rescans remove it again. This slice has no automatic scan or claim of a maximum cleanup delay.

## Capture barrier, snapshot and pins

`beginCapture({sourceRelease,sourceSchema})` takes only the maintenance gate and inserts a fresh capture. This short transaction commits **before** reference enumeration starts. Every capture insert/state/lease change advances the gate's actual generation tuple; GC locks that tuple last. Old RR snapshots therefore cannot miss a newly committed capture barrier. Capture begin never waits for business rows while holding the gate.

`captureReferences(captureId)` uses one bounded SQL statement to obtain the entire reference set and `pg_current_snapshot()` token together. It conservatively captures all persisted unfenced representations, including retained retired versions, rather than trusting caller-selected asset IDs. This is a READ COMMITTED transaction with a single statement's reference snapshot, **not a PostgreSQL export snapshot or database backup**. New representations after that statement belong to a later capture.

The same transaction inserts all pins in UUID order, then changes the capture from `capturing` to `pinned` and records its snapshot token/count. The previously committed barrier blocks GC throughout. The transaction does not lock the gate or capture record while waiting for asset locks. Each pin has composite FKs to immutable asset identity **and actual persisted size/digest metadata**. The pinned transition verifies the recorded count matches the actual pins. Overflow, pin failure, expiry or concurrent abort rolls all pins back and cannot publish a partial reference set. Unless explicitly aborted, the original barrier remains protective.

A pointer may be replaced after the reference statement. The former representation remains protected by the barrier, and then by its pin. RC allows its legitimate ready→retired transition without confusing that change with deletion; an actual permanent deletion fence still prevents pin creation. Tests observe a real blocked pin insertion before replacing the pointer, then verify that the original object is pinned and GC remains denied.

`readReferences` returns internal IDs/size/digest/source/snapshot metadata only for a currently pinned, unexpired capture and enabled DB maintenance policy. It contains no raw object key, bytes or public URL and must never be registered as a public API. A reference set does not prove the objects exist, that copies were made, that a DB dump uses the same snapshot, or that a backup is complete/usable. A future backup runner must bind an actual DB snapshot, copy and verify required objects, reconcile deletion policy and separately produce its manifest/restore evidence. This module has no `completeBackup` operation.

`renewProtection` extends only currently live capturing/pinned protection by the explicitly configured bounded duration. Expired protection cannot be revived. Decision-clock validation occurs again after the final potentially blocking gate-generation update. **Expiry fails closed:** expired capturing records and expired pins still block GC until an operator calls `releaseProtection(...,'abort'|'release')` after reconciliation. There is intentionally no TTL-based automatic unpin. This can block cleanup indefinitely and requires operational attention; it prevents expiry from silently destroying a reference being copied. Release/abort records and pin history remain immutable. Abort/release is allowed even when DB maintenance is disabled, but the constructor must still be explicitly enabled; no content is returned.

## Evidence and remaining work

[Maintenance tests](../../tests/runtime/asset-maintenance.test.ts) register `ASSET-MAINT-01`–`28`: disabled defaults, explicit retention, live pointers/intents, permanent fencing, RR stale snapshots for both asset and gate, effect-phase lock absence, late PUT/rescan, delete-before/after uncertainty, stale attempt, barrier→pin transition, overflow, real blocked-pin expiry/abort/replacement, GC-before-capture ordering, PG observation/capture failure, immutable verified metadata pins, current configuration, bounded renewals, competing claims, both GC/attach lock orders, and expiry during the final gate-generation wait. Lock tests inspect `pg_blocking_pids`; clock tests check the actual database clock rather than assuming elapsed sleeps imply ordering.

Tests do not establish cloud DELETE, production policy approval beyond the stated starting retention, backup retention policy, physical erasure, DB/R2 snapshot restore, quota release, a scheduler, real permissions or an enabled avatar cutover. The object examples here are synthetic opaque bytes; real image decoding remains the separate lifecycle/bridge tests' responsibility. Full local run counts belong in the integration handoff, not inferred from this checklist.
