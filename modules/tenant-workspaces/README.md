# Tenant workspaces

Tenant authority for one community member session. A tenant is not a user, a community, or a guild. Guild office and intern/full tier do not grant tenant access.

`authorization.ts` is the role matrix. `service.ts` performs the commands on the caller's transaction through the existing scoped command core. Tenant resource scopes are created inside `tenant.create` only.

Closed commands `tenant.create`, `tenant.invite.accept`, and `tenant.invite.decline` keep their receipts on the caller's personal scope. Create writes `freedom.tenant.created.v1` and the owner `freedom.tenant.membership.changed.v1` on that personal scope. Accept, `tenant.member.change`, and `tenant.member.leave` write `freedom.tenant.membership.changed.v1` (accept on the personal scope; change and leave on the tenant scope). Edit, workspace create, invite, decline, and revoke write the audit row and the receipt without a new outbox event. Workspace create does not bump `authorization_revision`.

Quotas in this slice: 5 active memberships in active tenants per person, 10 workspaces per tenant, 20 pending invitations per tenant, invitation expiry at most 7 days. Only `recovery_required` may have zero active owners; suspended and archived tenants still require one. Same-person `tenant.create` serialises on a transaction advisory lock (`tenant.create/v1/` plus the principal id) before the quota count. `tenant.member.change` does not return a revoked membership to active. Ownership transfer, fresh verification, and controlled recovery live in `ownership.ts`, `high-risk-verification.ts`, and `recovery.ts`. `security-path.ts` runs inside account deactivation. Account deactivation locks every active tenant this person owns, in tenant_id order, before it re-reads loginable owners. `bumpAuthorizationRevision` in `facts.ts` is the only revision bump and it invalidates a pending transfer in the same transaction.

There is no seeded authority policy. Without an active `tenant_authority_policies` row, fresh verification, transfer propose/accept, and recovery open/approve/execute/accept return `policy_unconfigured`. Cancel, decline, close, and reads still work. The local e2e harness inserts a synthetic policy (600, 86400, 86400, 1).

Accept and recovery-accept receipts stay on the recipient's personal scope. Disabling the last loginable owner sets `recovery_required` and does not grant the tenant to a guild leader or admin. Re-activation restores `active` only while the reason is still `owner_account_disabled`, no recovery case is `approved` or `executed`, and that person is still an active owner. Admin actions are also written to `platform_admin_audit`; `tenant_authority_audit` uses the affected person because that table cannot store an admin. Recovery execution and the security path insert the tenant journal directly because they are not scoped member commands. Membership facts for one transfer use aggregate types `tenant_membership` and `tenant_membership_prior` on the personal scope so the two events do not collide.

`GET /api/v1/tenants/invite-candidates?user_id=` resolves a visible same-community member to a person principal and may insert that person principal if mapping is missing. It never creates a tenant scope and never returns an email address.
