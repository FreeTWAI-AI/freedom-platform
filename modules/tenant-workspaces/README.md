# Tenant workspaces

Tenant authority for one community member session. A tenant is not a user, a community, or a guild. Guild office and intern/full tier do not grant tenant access.

`authorization.ts` is the role matrix. `service.ts` performs the commands on the caller's transaction through the existing scoped command core. Tenant resource scopes are created inside `tenant.create` only.

Closed commands `tenant.create`, `tenant.invite.accept`, and `tenant.invite.decline` keep their receipts on the caller's personal scope. Create writes `freedom.tenant.created.v1` and the owner `freedom.tenant.membership.changed.v1` on that personal scope. Accept, `tenant.member.change`, and `tenant.member.leave` write `freedom.tenant.membership.changed.v1` (accept on the personal scope; change and leave on the tenant scope). Edit, workspace create, invite, decline, and revoke write the audit row and the receipt without a new outbox event. Workspace create does not bump `authorization_revision`.

Quotas in this slice: 5 active memberships in active tenants per person, 10 workspaces per tenant, 20 pending invitations per tenant, invitation expiry at most 7 days. Only `recovery_required` may have zero active owners; suspended and archived tenants still require one. Same-person `tenant.create` serialises on a transaction advisory lock (`tenant.create/v1/` plus the principal id) before the quota count. The count runs before the new tenant context is bound. Create then inserts the explicit tenant id and tenant scope id. `tenant.member.change` does not return a revoked membership to active. Ownership transfer, fresh verification, and controlled recovery live in `ownership.ts`, `high-risk-verification.ts`, and `recovery.ts`. `security-path.ts` runs inside account deactivation. Account deactivation locks every active tenant this person owns, in tenant_id order, before it re-reads loginable owners. `bumpAuthorizationRevision` in `facts.ts` is the only revision bump and it invalidates a pending transfer in the same transaction.

There is no seeded authority policy. Without an active `tenant_authority_policies` row, fresh verification, transfer propose/accept, and recovery open/approve/execute/accept return `policy_unconfigured`. Cancel, decline, close, and reads still work. The local e2e harness inserts a synthetic policy (600, 86400, 86400, 1).

Accept and recovery-accept receipts stay on the recipient's personal scope. Disabling the last loginable owner sets `recovery_required` and does not grant the tenant to a guild leader or admin. Re-activation restores `active` only while the reason is still `owner_account_disabled`, no recovery case is `approved` or `executed`, and that person is still an active owner. Admin actions are also written to `platform_admin_audit`; `tenant_authority_audit` uses the affected person because that table cannot store an admin. Recovery open binds that tenant and its scope after the capability check. A case-id admin route binds `freedom.platform_admin_id` only after that check, reads the case tenant, then binds that tenant and its scope; recovery execution writes the tenant journal in that context. The security path lists the person's owner memberships with only the principal bound, binds each tenant and its scope for the status change, audit, journal and outbox, and clears that tenant before the next one. Pending transfers where this person is the recipient are invalidated with only the principal bound. A transfer this person sent is invalidated with that tenant bound: while the tenant is clear, the only transfer read policy matches the recipient, so the sender row would otherwise stay pending. A transfer recipient and a proposed owner bind the tenant with `bindTenantContext` because they may not be members. `listMyTransfers` and `listMyRecoveryCases` bind only the principal. Membership facts for one transfer use aggregate types `tenant_membership` and `tenant_membership_prior` on the personal scope so the two events do not collide.

`tenant_memberships.tenant_id` and `principal_id` are immutable. Ownership transfer has to change `role` on the same row or insert a new row. The deferred owner check locks every touched tenant in ascending `tenant_id` order. Private reads of one tenant go through `withTenantRead` (`packages/resource-scopes/index.ts`). The tenant list, invitation inbox, and invite-candidate reads call `assertCurrentSessionClock` after their row locks and before returning, and only when that read succeeded. A database error from the read keeps its SQLSTATE.

`GET /api/v1/tenants/invite-candidates?user_id=` resolves a visible same-community member to a person principal and may insert that person principal if mapping is missing. It never creates a tenant scope and never returns an email address.

## Ordinary instance grants and locks

`instance-grants.ts` validates and replaces the complete ordinary grant set. Operators may receive registered module keys; viewers receive only keys ending in `:read`. An entry includes a registered read key whenever the module has one. Admins and owners use role templates and hold no ordinary rows. Export, authority transfer, binding management, ownership transfer and instance management cannot be granted here. Purpose and expiry remain null. Unknown, foreign and unregistered targets return the same `capability_not_grantable` body. Invitations retain the canonical scope for the invitee and validate it again at acceptance; a stale scope changes nothing and returns `invitation_stale`.

Member change replaces all ordinary grants and bumps membership version and authorization revision even when only grants change. Removal revokes retained rows; re-grant reactivates the same permission id and advances its version. Unchanged active keys keep their version. Leave, ownership acceptance (both people), and recovery execution (restored and revoked owners) revoke active ordinary rows in the membership transaction. Account disable preserves memberships and grants.

Grant writers hold the tenant and target membership `FOR UPDATE` before changing rows. Work commands and private reads use `lockTenantScope` with tenant and membership `FOR SHARE`, so the grant set stays stable throughout that transaction and a revoke waits for an admitted request to finish. New memberships are inserted in that same tenant update transaction. Instance identities, module release references and registered definition keys are immutable; grant validation reads them without a row lock and never takes a `module_instances` lock. Members pages aggregate all grant entries in one query. Tenant-list projection binds each tenant through the same read resolver before reading its grants, then clears that tenant context.
