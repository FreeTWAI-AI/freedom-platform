# Closed runtime public-key enrollment

The adjacent [member-managed agent connection service](agent-connections.md)
records an enrolled runtime's fixed host client binding and expiry. It remains
separate from machine authentication and does not issue tokens or execution rights.
The [bootstrap JWT/DPoP verifier](bootstrap-proof.md) separately checks actual
signatures and exact purpose/binding. Its output is cryptographic evidence only:
no current DB authorization, nonce consumption, replay prevention or HTTP mount.
The separate [bootstrap status service](bootstrap-status.md) composes real proof
verification with current DB authority and atomic nonce/JTI admission for one
minimal status operation. It still has no token issuer, HTTP mount or execution
Grant, and it does not turn enrollment or crypto DTOs into reusable credentials.

The [device authorization coordinator](device-authorizations.md) now composes
fresh-device pairing, exact member approval, genuine enrollment proof and a
[constrained bootstrap issuer](device-pairing-proof.md). Its linked challenges
cannot be consumed through this older member `confirm` entry point: migration
090 requires their complete, original-deadline-bound one-time exchange. Ordinary
unlinked enrollment remains unchanged. This is an internal service, not mounted
device-flow HTTP or production key custody. Exchange now creates an initial
[refresh family](bootstrap-sessions.md) atomically. Its separate machine service
rotates one-use handles, commits family/connection revocation on verified reuse,
and issues fresh status nonces without a member cookie or an old nonce. These
operations still confer no execution authority; their [proof profiles](bootstrap-session-proof.md)
share the existing bootstrap access-token checks.

The explicitly constructed [bootstrap HTTP transport](../../apps/platform-api/src/routes/bootstrap-http.ts)
now connects these real services to closed JSON routes with origin/credential
separation, member cookie/CSRF, bounded body deadlines and independently committed
DB-clock request limits. [Profile 12](../../docs/platform-plan/execution/unified-foundation/12-bootstrap-http.md)
defines the wire contract. Production Node/Worker still do not mount the factory;
approved key custody, host/proxy settings and product UI remain outstanding.

`createRuntimeRegistrations(pool, { environment })` is an internal server factory
for current members. The host must explicitly select `local`, `staging-next`, or
`next`; there is no environment default or request override. It provides:

- `begin(actor, { key, publicJwk })`: generates runtime/challenge UUIDs and a public
  32-byte nonce, and returns the exact 300-second challenge payload to sign.
- `confirm(actor, { key, challengeId, proof })`: verifies actual ES256 possession
  and atomically consumes the challenge, inserts a registration and writes facts
  and a scoped command receipt.
- `read(actor, { runtimeDeviceId })`: reads only that member's registration metadata.
- `revoke(actor, { key, runtimeDeviceId, expectedVersion })`: permanently revokes
  using an exact decimal aggregate version; matching receipt retries are safe.

All returned objects carry `operational_authority: false`. Enrollment proves
member approval and possession of the corresponding private key under this closed service; it
does not attest a runtime build, hardware, capability, provider, model, official
CLI login, or permission to execute. The enrollment factory has no HTTP mount,
machine validator, token, Grant, Attempt, lease, provider call, or dispatch. Actor must
come from trusted server member authentication, not caller JSON. Every operation
rechecks active user/session/person/personal scope and completed required onboarding.
Read/revoke have no model or private-work persistence-policy dependency.

The [central engineering profile](../../docs/platform-plan/execution/unified-foundation/07-runtime-enrollment.md)
fixes the exact EC P-256 JWK, ES256 JWS header and server payload bytes. Public JWKs
are imported with `jose` to reject invalid curve points. Private keys are never
accepted by the public-JWK parser or generated by this service. Raw JWS proofs
are not saved in any table, journal, outbox or receipt; only their SHA-256 enters
the confirm command digest. Nonces are **public challenges**, not bearer secrets:
the begin receipt intentionally retains the public challenge for exact replay.
A nonce without the private key and a current member session grants nothing.

## Transactions and immutable identity

Migration [087](../../migrations/087_runtime_registrations.sql) is provisional.
Both real tables have non-null person/user and personal-scope composite FKs.
Challenge identity and registration owner/environment/key/runtime identity are
immutable. Challenge consumption is one-time. Registration state is only
`enrolled`/`revoked`; the latter is terminal. DELETE is prohibited, preserving
the environment/key unique tombstone. A rotated key needs a fresh server runtime
identity; pending public challenges do not reserve keys or prevent another member
who actually holds the private key from confirming.

Lock order is current user → session → person → personal scope → scoped command
advisory → owner/environment advisory → key advisory → challenge → registration.
Read omits the command advisory. Scope stays `FOR SHARE`; no scope lock upgrade
or callback-supplied authorization flag exists. Owner/environment serializes the
fixed per-owner caps: 10 current pending challenges, 1,000 lifetime challenges,
32 registrations including revoked entries. The separate environment/key advisory
and SQL unique constraint serialize competing owners of the same key.

Session validity is refreshed using PostgreSQL `clock_timestamp()` after domain
locks and after asynchronous cryptography. New confirmation rechecks expiry at
the final database decision time, with no grace period. Issuance uses the database
clock truncated to milliseconds. Expired/consumed begin receipts are denied.
An exact successful confirm replay may outlive challenge expiry, but it must
still pass current owner/session checks and the registration must remain enrolled.
New receipt keys cannot consume an old challenge, and revocation blocks both
begin and confirm replay from reporting renewed enrollment.

SQL enforces structural identity, FK, one-consumption, version and tombstone
invariants. Its registration trigger qualifies backing rows with `TG_TABLE_SCHEMA`
so TEMP/search-path shadows cannot replace the physical challenge. SQL does not
verify ES256: cryptographic admission belongs to the trusted service. Possession
of an app database write credential is outside the owner-ACL threat model; a
database row itself must never be accepted as machine authority. Trigger protection
does not cover a privileged schema owner disabling triggers or truncating history.

## Local evidence

[Runtime registration tests](../../tests/runtime/runtime-registration.test.ts)
exercise real PostgreSQL and actual ES256 signatures, exact retry, simultaneous
begin/confirm/revoke, cross-owner public-key squatting, environment isolation,
current-member revocation, bounded input, all three fixed quotas and atomic
rollback of each journal/outbox/receipt sink. They require an explicit disposable
`fp_*` database and create/remove a dedicated schema; they never fall back to a
default database. The separate proof and adversarial/grants suites cover malformed
cryptography, lock barriers and low-privilege SQL behavior.

These local checks are not evidence of deployment, packaged browser/native
support, hardware protection, production grants, or full device-flow/DPoP acceptance.

The [authenticated broker bridge](../../docs/platform-plan/execution/unified-foundation/19-authenticated-broker-bridge.md)
adds server-only original-session command authorizations. Its signed wire contains
only references, nonce, digest, purpose and deadlines. SQL derives the broker-local
Actor from the original genuine session; JSON cannot supply one. One-use claim
admission does not replace the existing ModelStep dispatch claim or stage CAS.
