# Bootstrap session cryptographic profiles

`createBootstrapSessionProofVerifier(host)` snapshots a strict `BootstrapSessionHost` and exposes only `verifyRefresh` and `verifyNonce`. The configured HTTPS ASCII refresh and nonce URIs are canonical, distinct from each other and the GET bootstrap URI, and never fetched. `parseBootstrapSessionHost` is the same fixed configuration parser used by the trusted service.

Refresh accepts `{proof,publicJwk,familyId,generation,connectionId,refreshHandleHash,nowMs}`. The supplied durable generation/key binding must match every signed field. It requires no access token, so an expired short-lived token does not prevent refresh. The wire hash is SHA-256 base64url of the raw canonical refresh handle; it is not DPoP `ath`.

Nonce acquisition accepts `{accessToken,proof,expectedBinding,nowMs}`. It verifies the exact access token with the same server-internal crypto helper used by the existing GET verifier, then verifies the separate nonce purpose, device key, POST URI, connection and exact token hash. It neither fabricates a GET proof nor consumes or requires an existing status nonce.

Both methods reject malformed input with `null`, snapshot before awaits, reject executable properties, strictly parse compact JOSE JSON, and perform actual ES256 verification with public P-256 keys. Proof types and purposes cannot cross between refresh, nonce acquisition, device pairing and GET DPoP. Proof time uses the existing floor-based `[-60,+5]` seconds window expressed as exact `[validFromMs,validUntilMs)` bounds; nonce additionally intersects token and issuer-key validity. Unrepresentable refresh intervals fail closed. Configuration errors throw a fixed `BootstrapSessionProofError` without echoing configuration or secret material.

Results are frozen and contain only proof ID, interval and `assurance:'cryptographic_only',operational_authority:false`; nonce also returns token ID. Host keys, clock and expected binding remain trusted-server assumptions. Repeating a valid proof, including its ECDSA high-S/low-S equivalent, can succeed here. The session service must hold current identity/connection/family locks, recheck DB time after crypto awaits, and atomically store proof JTIs and nonce/rotation/reuse transitions. This module grants no execution authority, performs no remote key discovery and stores no secrets.

The pure runtime suite uses ephemeral, nonextractable issuer/device private keys and real signatures, including signed substitutions, strict framing, mutation, time boundaries and equivalent signatures. It does not establish production issuer custody, transport security, current DB authority or operational readiness. The canonical service protocol is [spec 11](../../docs/platform-plan/execution/unified-foundation/11-bootstrap-sessions.md).
