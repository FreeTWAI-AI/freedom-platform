# Existing shop service boundary

The member commerce routes manage an existing owner's shops and opaque credentials. The separate `/shop-api/v1` bearer routes act for that shop, never as the owner's login, private Work or model authority. [orders.ts](orders.ts) preserves the current create/payment business dedupe and dynamic projections. [service-command.ts](service-command.ts) connects the existing cancellation operation to the common transaction, receipt and scoped journal. This is not a new commerce feature or generic service framework.

The server resolver and schema constraints are documented in [resource-scopes](../../packages/resource-scopes/README.md). After schema 117 and 118, an upgraded issuer creates only purpose-bound v2 keys when the owner explicitly requests issuance. Its existing member receipt/digest stays unchanged and a replay still returns `token: null`. The application must receive an explicit `FREEDOM_SHOP_KEY_POLICY=legacy-compatible` or `purpose-bound-only`; absent configuration yields shop-only 503. The Worker config checker lists this as a required injection without changing deployed vars. `/api/v1/health` reports the actual selected policy and issuer profile, or `unconfigured`/null. A merged source SHA or configured example is not an installed policy observation.

## Controlled legacy exit

Run `node --import tsx scripts/shop-key-legacy-exit.ts --plan` for a plan that reads no connection or target. An explicitly selected, reviewed tool can run `--execute-readonly --host-bindings /outside/repository/private-targets.json`. The regular, owner-only file must contain exactly two target expectations with `environment` (`public` or `staging`), HTTPS `origin`, reviewed full `sourceSha`, and expected database `host`, `port`, `connectionUser`, `database`, `schema`, and dedicated read-only SQL `role`. A provider routing username such as `role.branch-id` must be selected explicitly and is not the observed SQL role. It cannot supply installed observations. Keep this file and credentials outside version control. The only accepted connections are explicitly supplied `FREEDOM_SHOP_EXIT_PUBLIC_DATABASE_URL` and `FREEDOM_SHOP_EXIT_STAGING_DATABASE_URL`; remote URLs require verified TLS and cannot override host/options. There is no `.env` or ambient `DATABASE_URL` discovery.

[key-exit.ts](key-exit.ts) independently reads each selected health endpoint before and after its SQL observation. It requires the exact approved release, explicit actual policy, and `freedom.shop-service-key/v1` issuer profile. Redirects (including Access), missing fields, stale releases or oversized responses are unavailable, not inferred from source. SQL checks current database/schema/session role, a non-superuser/non-bypass role, transaction read-only mode, and a real unfiltered table. Each target has a bounded repeatable-read observation of at most 10,000 active keys. Token hashes are compared only in memory; reports contain counts and binding/report digests, never hashes or credentials. The target guard compares the selected endpoint (including an explicit routing suffix or local fixture socket), database and schema; opening the same endpoint twice under two plain SQL roles is not a second target. The private target factory checks the actual URL against host/port/routing expectations and keeps its pool inaccessible to caller replacement. It uses explicit TLS and a password callback, without `PG*` or `.pgpass` credential fallback. Provider physical branch identity and the completeness of the selected inventory remain operator observations, not an inference from SQL names.

An active legacy key, invalid bound tuple or active hash shared across the two selected environments blocks exit. Rotate an affected key through its existing owner-authorized endpoint; never stamp the same unbound hash as belonging to both environments. Expired/revoked rows remain untouched. Even a clear report means only `eligible_for_review` for the selected endpoints and always reports `legacy_exit: false` and `deployment_authority: false`. Observations are not a global inventory, continuous writer lock or rollout authorization.

The operator must separately verify the complete active/retained issuer inventory and rollback floor, then approve and observe `purpose-bound-only` on both environments. Old issuers that cannot verify the binding cannot remain an allowed rollback. Re-observe the exact release/policy after rollout and retain the client compatibility evidence. This packet does not rotate live keys, discover provider configuration, change policy or assert that this operational exit has happened.

## Validation scope

The isolated [identity](../../tests/runtime/shop-service-identity.test.ts), [command](../../tests/runtime/shop-service-command.test.ts), and [exit adapter](../../tests/runtime/shop-key-exit.test.ts) tests require an explicit disposable loopback `fp_*` PostgreSQL database. They use synthetic owners/keys, real HTTP handlers/servers and SQL transactions/locks, including restricted LOGIN roles. Their sources are not evidence of a particular execution; recorded commands, source hashes and results belong in the integration evidence. No test here targets production or demonstrates live legacy retirement, general service authority, all commerce common-command coverage or model broker authorization.

## Hosted stores

The `storefront` module uses the existing commerce tables. A hosted store has two `commerce_shops` rows with `origin='hosted'`: an internal supply shop for items and a public storefront shop for selections. `commerce_resource_tenants` maps each shop to its tenant and instance under tenant RLS. The original acting person principal is saved as `source_owner_id`; readers never infer this historical identity from the current member. Private profile, publication and product reads join confirmed mappings under a session-bound tenant context. Registry provisioning creates no shop; the separate setup command creates both shops, mappings and the profile atomically.

Profiles hold the slug and current publication pointer. Publications preserve immutable revisions containing only the public name, brand, description, currency, ordered product display fields and publication metadata. [hosted/public.ts](hosted/public.ts) is the single anonymous reader: its read-only transaction resolves the explicit publication and active owner, then binds a principal-less tenant context to check active tenant/instance and the confirmed shop mapping under RLS. Anonymous readers receive the stored allowlist, never live item rows or tenant/member identifiers. Profiles and publications are outside RLS specifically for that reader; every private read remains anchored to an RLS relation.

Hosted stores support at most 200 products, names and brands up to 80 characters, titles up to 120 and descriptions up to 2000. Prices are positive integer minor units up to 100000000 in TWD or USD, and stock is 0..1000000. SKUs increase monotonically and are never reused. Product updates change item and selection together without changing the store version. Shipping and return terms explicitly say they are unset, shipping is zero, photos are absent and no distribution acceptance is written. Publishing snapshots the draft; identical republishing creates no revision. Slugs become permanently fixed at first publish, including after unpublish.

Ordering is not enabled. Hosted shops remain test mode with `accepting_orders=false`, empty website and contact; a database CHECK enforces those values. The public `/shops/:slug` page displays 「店鋪／商品展示已就緒，交易尚未啟用」. Legacy catalogs, import selection, kits, owner routes, public-shop routes and shop-service credential resolution accept only `origin='imported'`. A hosted shop cannot issue a legacy key or enter the legacy order/payment path.

For cleanup, delete selections first, then items, then both shops. The profile and its publications cascade from the shops, and resource mappings cascade from each shop. Profile identity/slug and publication immutability triggers only reject updates; deletes remain available for erasure and test cleanup. The migration registers the module/application without a guild offering; a later slice provides the member launch UI and offering. All new routes require the existing guild-launchpad release flag.

Member UI: commerce members enter from the launchpad’s 「建立我的商店」 primary action, the 「我的商店」 tab, or 「設定我的商店」 after the existing launch flow succeeds. `#stores` lists readable stores; `#stores/<tenant_id>/<instance_id>` provides setup, product editing, preview and publication. This UI only calls the existing hosted-store API; ordering remains disabled.
