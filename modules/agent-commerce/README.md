# Existing shop service boundary

The member commerce routes manage an existing owner's shops and opaque credentials. The separate `/shop-api/v1` bearer routes act for that shop, never as the owner's login, private Work or model authority. [orders.ts](orders.ts) preserves the current create/payment business dedupe and dynamic projections. [service-command.ts](service-command.ts) connects the existing cancellation operation to the common transaction, receipt and scoped journal. This is not a new commerce feature or generic service framework.

The server resolver and schema constraints are documented in [resource-scopes](../../packages/resource-scopes/README.md). After schema 117 and 118, an upgraded issuer creates only purpose-bound v2 keys when the owner explicitly requests issuance. Its existing member receipt/digest stays unchanged and a replay still returns `token: null`. The application must receive an explicit `FREEDOM_SHOP_KEY_POLICY=legacy-compatible` or `purpose-bound-only`; absent configuration yields shop-only 503. The Worker config checker lists this as a required injection without changing deployed vars. `/api/v1/health` reports the actual selected policy and issuer profile, or `unconfigured`/null. A merged source SHA or configured example is not an installed policy observation.

## Controlled legacy exit

Run `node --import tsx scripts/shop-key-legacy-exit.ts --plan` for a plan that reads no connection or target. An explicitly selected, reviewed tool can run `--execute-readonly --host-bindings /outside/repository/private-targets.json`. The regular, owner-only file must contain exactly two target expectations with `environment` (`public` or `staging`), HTTPS `origin`, reviewed full `sourceSha`, and expected database `host`, `port`, `connectionUser`, `database`, `schema`, and dedicated read-only SQL `role`. A provider routing username such as `role.branch-id` must be selected explicitly and is not the observed SQL role. It cannot supply installed observations. Keep this file and credentials outside version control. The only accepted connections are explicitly supplied `FREEDOM_SHOP_EXIT_PUBLIC_DATABASE_URL` and `FREEDOM_SHOP_EXIT_STAGING_DATABASE_URL`; remote URLs require verified TLS and cannot override host/options. There is no `.env` or ambient `DATABASE_URL` discovery.

[key-exit.ts](key-exit.ts) independently reads each selected health endpoint before and after its SQL observation. It requires the exact approved release, explicit actual policy, and `freedom.shop-service-key/v1` issuer profile. Redirects (including Access), missing fields, stale releases or oversized responses are unavailable, not inferred from source. SQL checks current database/schema/session role, a non-superuser/non-bypass role, transaction read-only mode, and a real unfiltered table. Each target has a bounded repeatable-read observation of at most 10,000 active keys. Token hashes are compared only in memory; reports contain counts and binding/report digests, never hashes or credentials. The target guard compares the selected endpoint (including an explicit routing suffix or local fixture socket), database and schema; opening the same endpoint twice under two plain SQL roles is not a second target. The private target factory checks the actual URL against host/port/routing expectations and keeps its pool inaccessible to caller replacement. It uses explicit TLS and a password callback, without `PG*` or `.pgpass` credential fallback. Provider physical branch identity and the completeness of the selected inventory remain operator observations, not an inference from SQL names.

An active legacy key, invalid bound tuple or active hash shared across the two selected environments blocks exit. Rotate an affected key through its existing owner-authorized endpoint; never stamp the same unbound hash as belonging to both environments. Expired/revoked rows remain untouched. Even a clear report means only `eligible_for_review` for the selected endpoints and always reports `legacy_exit: false` and `deployment_authority: false`. Observations are not a global inventory, continuous writer lock or rollout authorization.

The operator must separately verify the complete active/retained issuer inventory and rollback floor, then approve and observe `purpose-bound-only` on both environments. Old issuers that cannot verify the binding cannot remain an allowed rollback. Re-observe the exact release/policy after rollout and retain the client compatibility evidence. This packet does not rotate live keys, discover provider configuration, change policy or assert that this operational exit has happened.

## Hosted stores

The `storefront` module uses the existing commerce tables. A hosted store has two `commerce_shops` rows with `origin='hosted'`: an internal supply shop for items and a public storefront shop for selections. `commerce_resource_tenants` maps each shop to its tenant and instance under tenant RLS. The original acting person principal is saved as `source_owner_id`; readers never infer this historical identity from the current member. Private profile, publication and product reads join confirmed mappings under a session-bound tenant context. Registry provisioning creates no shop; the separate setup command creates both shops, mappings and the profile atomically.

Profiles hold the slug and current publication pointer. Publications preserve immutable revisions containing only the public name, brand, description, currency, ordered product display fields and publication metadata. [hosted/public.ts](hosted/public.ts) is the single anonymous reader: its read-only transaction resolves the explicit publication, then binds a principal-less tenant context and, under RLS, checks the active tenant and instance, the confirmed shop mapping, and that the tenant currently has at least one active owner who is not a verification test account. The account that ran setup plays no part in public liveness. Anonymous readers receive the stored allowlist, never live item rows or tenant/member identifiers. Profiles and publications are outside RLS specifically for that reader; every private read remains anchored to an RLS relation.

Hosted stores support at most 200 products, names and brands up to 80 characters, titles up to 120 and descriptions up to 2000. Prices are positive integer minor units up to 100000000 in TWD or USD, and stock is 0..1000000. SKUs increase monotonically and are never reused. Product updates change item and selection together without changing the store version. Shipping and return terms explicitly say they are unset, shipping is zero, photos are absent and no distribution acceptance is written. Publishing snapshots the draft; identical republishing creates no revision. Slugs become permanently fixed at first publish, including after unpublish.

Ordering is not enabled. Hosted shops remain test mode with `accepting_orders=false`, empty website and contact; a database CHECK enforces those values. The public `/shops/:slug` page remains a script-free display with a non-payment/non-shipping notice and a neutral link to authenticated reservation status. Legacy catalogs, import selection, kits, owner routes, public-shop routes and shop-service credential resolution accept only `origin='imported'`. A hosted shop cannot issue a legacy key or enter the legacy order/payment path.

For stores without order history, delete selections first, then items, then both shops. The profile and its publications cascade from the shops, and resource mappings cascade from each shop. Profile identity/slug and publication immutability triggers only reject updates; order/quote/line foreign keys now retain referenced history; erasure policy remains undecided. Test cleanup uses isolated schema teardown. The migration registers the module/application without a guild offering; a later slice provides the member launch UI and offering. The hosted-store management and anonymous publication routes require the existing guild-launchpad release flag. Exact private buyer order recovery/cancel has a separate member boundary, described below.

Member UI: commerce members enter from the launchpad’s 「建立我的商店」 primary action, the 「我的商店」 tab, or 「設定我的商店」 after the existing launch flow succeeds. `#stores` lists readable stores; `#stores/<tenant_id>/<instance_id>` provides setup, product editing, preview and publication. This UI only calls the existing hosted-store API; ordering remains disabled.

## Direct-sale reservation candidate

[HO-0](hosted/direct-order-contract.md) defines the member quote/submit/read/cancel DTOs. HO-1/2 adds provisional migration 138 and closed backend services in `hosted/direct-authority.ts`, `direct-quotes.ts`, `direct-orders.ts` and `direct-effects.ts`. The candidate parents include real 136/137; no applied migration is rewritten. The migration adds immutable quotes and a direct discriminator/private buyer relation to the SAME orders/lines authority; stock remains `commerce_items.stock/reserved`. Default `reservation_enabled=false`, the original hosted `accepting_orders=false` CHECK and every public/UI transaction-disabled flag remain intact. The following HO-3 candidate adds only member buyer HTTP routes; no application release, seller order capability, payment or fulfilment activation is registered.

An ordinary buyer may belong to another community and never receives a seller tenant membership/context. The closed adapter holds the actual member personal scope, then binds only the exact store tenant for RLS after resolving publication or persisted buyer/order ownership. It checks both shop mappings and current tenant/scope/instance/deployment/owner authority. Owner-account changes already lock owned tenants in `tenant-workspaces/security-path.ts`. Hosted edits and reservations share instance → commerce community → profile → quote/order → sorted item locks. Stock below reserved returns a domain conflict. Imported callers retain their existing commands and semantics.

A five-minute quote makes no reservation. Submit creates one thirty-minute reservation identified by the buyer intent and immutable terms. Receipts contain only its ID; the closed transaction runner rechecks authority and projects current state on the same client. Fresh quote and session decision clocks are checked after receipt waits, with a conservative monotonic fence. Existing committed intents do not need an unexpired quote. Quote/submit first expire only the physical shortfall for requested items: at most 99 old orders per item and 50 requested items, all selected order locks before sorted affected item locks. This avoids rollback starvation behind an unrelated global expiry batch. Cancel and read can release expired stock under the actual member identity; each reserved order has one terminal transition and version increment. Pause/archive blocks new orders, while exact buyer history/release still works through retained mappings. Private authoritative reads use a stable ID-only receipt per buyer/order and per buyer/shop/intent (at most two read receipts per order), with current ACL/projection/expiry on every poll and no receipt for absence; no unauthenticated background actor or worker is invented.

`tests/runtime/hosted-direct-orders.test.ts` exercises restricted PostgreSQL roles, cross-community buyers, stock races, all-line rollback, current-state retries, historical expiry and a real receipt INSERT barrier. Synthetic fixture activation is not a production configuration path or live acceptance. The HO-4 revision below adds owner-only seller list/cancel. Buyer pagination, delegated seller order capabilities, anonymous readiness, contact datasets and destructive TTL cleanup remain absent. Payment/refund/fulfilment remain false; no supplier acceptance, transfer or payable is invented for direct sale.

### HO-3 buyer HTTP candidate

The session-only [buyer routes](../../apps/platform-api/src/routes/hosted-orders.ts) expose readiness, quote, submit, exact own-order/by-intent recovery and buyer cancel using the HO-0 DTOs. All responses, including authentication errors, are private/no-store. Mutations use the existing same-origin CSRF boundary and idempotency headers; cancellation also requires a quoted version ETag. Strict bodies and query parsing reject unknown or repeated parameters. Shop bearer credentials are never member sessions.

Discovery/readiness and new quote/submit routes retain the existing guild-launchpad installation flag. A separate `FREEDOM_HOSTED_RESERVATIONS_ENABLED` host setting enables admission only for the exact string `true` in Node and Worker; absent or any other value is OFF. The Node embedding option similarly requires boolean `true`. Readiness is generic and false when host admission is OFF; when ON it also checks the current member, publication, installation/mapping and separate per-store `reservation_enabled` setting. It never reserves stock. No configuration, provisioning, publication or migration here enables either setting.

Exact own-order GET/by-intent and buyer cancel stay mounted after the real member boundary when either host flag is OFF. They still require the current eligible member and persisted order/mapping authority; missing schema or configuration cannot grant access. Submit returns 201 only for a newly committed order and 200 for current same-intent recovery, including a different transport key. Receipts remain ID-only. Public storefront DTOs and their transaction-disabled display remain unchanged.

`hosted-order-http.test.ts` is the isolated real-socket session/CSRF/ACL/flag/replay verification suite; `hosted-order-http-contracts.test.ts` checks exact Node/Worker flag injection and rejects bearer-only recovery without a database connection. Execution evidence is recorded separately. HO-12 and this HO-3 candidate are not yet main integration, deployment or live acceptance.

### HO-4 owner-only reservation management candidate

The seller list/read/cancel slice uses the current genuine tenant owner and the exact installed storefront release's existing `store:manage` capability. Admins, delegated operators/viewers, store-only grants and guild titles cannot obtain order access. This explicitly narrows the earlier HO-0 granular proposal: `store:orders.read/cancel` are not installed, and no release pin, migration, grant template or reservation setting is changed.

The closed tenant adapter rechecks real owner/mapping authority before receipt access and after same-client current projection. Receipts retain only IDs; stable list-read identity never stores page DTOs or keys per poll. Each page revalidates its current signed cursor/query after ACL, uses the shared tenant-list codec, and fails closed on page one without a configured key. Retained history/cancellation remains available when admission/discovery is OFF and for suspended/archived instances, while disabled scope or revoked owner/session still refuses. Cancellation/expiry share the existing physical reserved balance and record facts with the real tenant context; no buyer context is manufactured. These candidates are not live acceptance.
### Buyer member UI candidate

`#reservations` accepts an own-order reference; it is not a full history list. Public shops link to `#reservations/<slug>` without embedding buyer data. Strict readiness true is required before quote or submit controls appear. A five-minute server quote is reviewed before an explicit thirty-minute stock reservation; goods amounts are not an amount due. No payment, contact/address or fulfilment flow is added.

Before submit, the member page places only the opaque intent and store slug in its recovery hash and holds the exact body/key in memory. Unreadable successful responses and network failures remain unknown; retries keep the tuple and current own-order reads confirm server state. Pending/unknown commands protect app navigation. Full-page close only warns; no private cart/body is persisted. Fresh login uses the original intent/order locator to read authorized server state and never auto-submits. Other accounts cannot inherit the in-memory result. Own read/by-intent/cancel remain reachable regardless of new-reservation admission. A stale cancellation refreshes current state for review; it does not silently replace the original version/key.

This is local candidate UI source, not activation or live acceptance. Runtime/browser execution evidence remains separate.
