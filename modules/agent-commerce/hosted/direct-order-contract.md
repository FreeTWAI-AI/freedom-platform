# Hosted direct-sale reservation — HO-0

This is a reviewable contract/design, not an enabled API, migration, application release or live acceptance. Source baseline is PR #302 `7becd8a3dd284ea8f4aea6889efa381b1e1181a0`. Direct sale of the member's own hosted goods is the accepted next scope. Ordinary buyers may be outside the seller tenant/community. No supplier acceptance, transfer, payable, receipt of money or shipment is manufactured.

Canonical DTOs: [hosted-order.ts](../../../contracts/guild-launchpad/v1/hosted-order.ts); generated structural bundle: [hosted-order.schema.json](../../../contracts/guild-launchpad/v1/hosted-order.schema.json). The profile is `freedom.hosted-direct-order-reservation/v1`. Schema parsing grants no permission and proves neither current stock nor a committed order. Cross-field totals, duplicate SKU and time checks are listed as server-only rules in generated schemas.

## Product boundary

The eventual slice is a real, authenticated member order in `commerce_orders` with `state=reserved`, then `cancelled|expired`; it is not an imported shop's `mode=test|live` payment flow. Quote has `reserves_stock=false`. Order state means actual local stock reservation, not seller acceptance, paid, shipped or fulfilled. Payment/refund/fulfilment/money movement remain literal false. `merchandise_total_minor` is the quoted goods amount only; `amount_due_minor=null`, shipping not configured and tax not assessed. No delivery address, email, telephone, free-form contact, CRM record or external delivery reference is requested. The member principal/order relation stays private; neither buyer email nor principal ID enters public projection or the other party's DTO.

HO-0 leaves `StoreView.transaction_state`, public projection, the application release and all existing routes unchanged. A future reservation-specific readiness endpoint may report enabled only when the explicit per-store reservation setting, compatible installed schema/service, active seller tenant/instance/deployment/owner, publication and current caller eligibility all hold. Metadata descriptors are file ownership, not an application release. No automatic activation on merge, provision or publish. Readiness never promises a particular item's availability.

## Proposed wire surface (not registered)

All routes are same-origin, session authenticated, private/no-store; mutations require current CSRF and `Idempotency-Key` (8–128 ASCII `[A-Za-z0-9_-]`). Read endpoints reject unknown/duplicate query keys; body DTOs are strict, including nested objects. No cookies, bearer keys, owner IDs, tenant IDs, price, currency or capability are accepted from a buyer body. `fw_read_` and `fw_shop_` are not member sessions.

| POST `/api/v1/hosted-stores/:slug/quotes` | `QuoteInputSchema` → `QuoteSchema`, 201 | Active eligible member, current active public store, reservation setting; no seller tenant membership. 1–50 distinct SKUs, quantity 1–99. |

The two proposed seller capabilities must be registered deliberately in the later release/schema slice; owner/admin template can include them then. Existing `store:write/publish`, viewer role, guild title or a grant on another instance cannot imply them. Seller DTO exposes order/reference/line facts only, no buyer contact or directory enrichment. Buyer and seller use the same order ID; the order never becomes a tenant Work. Signup, guild onboarding and member privacy rules remain unchanged; no additional guild/tenant membership is silently created.

## Quote and retry identity

Use a bounded persistent quote sidecar of agent-commerce, not a second order table or stock balance. Proposed `commerce_order_quotes` stores immutable quote UUID, buyer principal, exact existing storefront shop + confirmed tenant/instance mapping, publication ID/revision, selected item/selection IDs and versions, canonical public terms digest, timestamps and eventual consumed order reference. These private bindings are not returned as buyer-editable fields. Quote writes no order, reserve, supplier transfer or financial event. A five-minute quote uses DB `clock_timestamp()`; idempotent quote retry returns the same quote/deadline, never prolongs it. Cap unconsumed, unexpired quotes at 10 per buyer/store and rate-limit quote creation to 20/minute per buyer through the existing auth limiter; bounded expired-quote cleanup cannot delete any consumed quote/order lineage or command outcome.

`terms_sha256` hashes a server-canonical object including profile, buyer binding, exact shop/mapping/publication, selection versions, currency, quantities, current prices and explicit disabled delivery/payment terms. No caller-defined JSON or display HTML participates. Public projection remains immutable. Resolve published SKU to current selection/item in the same mapped shop. If any requested current title/price differs from that publication, return 409 `publication_changed` and require republish/review; do not silently quote an unpublished new price. Current stock is read separately and never added to public publication.

Submit body contains only `quote_id`, reviewed `terms_sha256`, and stable UUID `client_order_id`. The latter names the buyer intent across lost responses; server forms a collision-free external ID from the buyer principal UUID + intent UUID (fixed encoding within the legacy 100-character bound). Preserve existing `(public_shop_id,external_id)` uniqueness and add explicit profile/buyer/intent unique evidence as needed. Changing the transport key cannot duplicate a consumed quote: the same quote + buyer intent returns its existing order; another intent using that consumed quote is 409 `quote_consumed`. Same intent with different quote/digest conflicts, even if the old order has expired/cancelled. A new purchase requires a new quote and intent; same-ID retries never resurrect or extend reservations.

Scoped command receipt should retain only the stable order ID/outcome reference, not a stale `reserved` DTO. Authenticate/authorize before any receipt read. On receipt hit, recheck current identity and read current authorized order state; quote expiry is checked for a NEW effect, not used to hide an already committed order on retry. If store pause blocks submission/replay, buyer's existing order GET and cancel still remain available. A network error is unknown result: reuse exact intent/body/key or read by the same authenticated intent lookup; never create a new key/order automatically. The private `GET /api/v1/me/hosted-orders/by-intent/:client_order_id?store_slug=...` lookup is part of this recovery contract; exact buyer and shop required, 404 means authoritative absence, not a timeout.

## Single transaction and locks

Current imported commands rely on `lockShopService` taking `commerce-orders/{community_id}` before entering `createOrder/payment/cancelOrder`; those functions are not independently safe public ports. Hosted product edits currently lock profile then edit `commerce_items`. A hosted order must not introduce a competing stock writer or call `createOrder` after stripping `origin='imported'`.

For the later implementation, use existing `runCommandCore` and isolated transaction ownership. Buyer commands use their real member session/person and personal receipt namespace with a closed domain adapter; they MUST NOT construct seller `TenantScopeContext`, impersonate an owner or grant membership. Seller commands use existing `scopedTenantCommand`. Any tenant RLS binding for the public-store operation is a server-controlled exact target, after explicit public-store/order relation checks, not arbitrary tenant access. Separate personal receipt provenance from seller dataset ownership in the module-data catalog.

Lock order for hosted paths (skip unused steps, never reverse):

1. Actual caller user/session/person and personal scope, or existing seller tenant scope/membership; receipt advisory lock follows that adapter's current order.
2. Resolve exact mapping; seller tenant/scope lifecycle share lock, instance lock then deployment share lock (same order as hosted lifecycle). Buyer path checks active owner through the current tenant authority revision under tenant share lock, without acquiring another user's actor identity. HO-1 must verify all owner/status mutators take the conflicting tenant lock; otherwise add a reviewed liveness lock seam, never assume a snapshot closes revoke races.
3. Existing `commerce-orders/{seller community_id}` advisory lock, then hosted profile row, then exact quote / existing order row, then distinct selection/item rows in UUID order. No path holds community lock and then requests a hosted instance lock. Imported paths keep community→imported shop and cannot reach hosted rows.
4. Check current mapping/publication/quote buyer+digest+expiry and current prices/selection versions; expire pending hosted reservations through the same effect path while holding community lock; lock affected order/items in deterministic order. Check every quantity against `stock-reserved` before ANY line reserve. All lines, existing order/lines, private buyer relation, reservation state, scoped receipt/journal/outbox commit or roll back together. No remote I/O.
5. After receipt storage or other waits, recheck current session and DB decision clock. A new effect that crossed quote expiry rolls back, including receipt. Existing outcome lookup uses order ACL and does not renew quote. CAS comparison for a fresh cancel is after receipt lookup, so same-key retry with original version is valid; new key with stale version is 412.

All hosted product add/update/remove and publication/enable changes must join this same instance→community→profile ordering before this slice enables orders. Stock edit below reserved is a controlled conflict, not an uncaught CHECK exception. Item deletion with order history stays prohibited. Imported functions and their existing guards remain intact; factor their local reserve/release logic into one agent-commerce effect seam only as necessary, with compatibility regressions. No `inventory_balances`, second ledger, external binding or inventory port is created. SP-10's future authority transfer remains a separate slice.

## State, expiry and suspension

Quote → successful submit creates ONE existing order, version 1, state reserved, deadline DB creation time + 30 minutes. A direct order's reservation state is distinct from legacy `buyer_payment`; buyer DTO always says payment not enabled. Fresh cancellation takes order lock + version CAS, releases each line once and changes state/version/closed_at. Repeated same-key cancellation returns current state; a new key targeting terminal cancelled/expired state is a no-op only with current version. If deadline has passed, expiry wins and response says expired, never buyer-cancelled.

Expiry is an explicit bounded internal agent-commerce operation, not an unauthenticated HTTP cron. It takes the same community→order→item locks, rereads DB time, and transitions only reserved→expired. It never uses a fake member actor; record an actual configured system operation identity (no new general service framework). If an operator identity is unavailable, release can still be performed by the authenticated create/read/cancel transaction with an honest expiry reason, rather than inventing a system actor. New create first processes expired reservations for the addressed shop; order GET/status performs bounded authoritative expiry before returning (private, no cache). Thus an expired order is never reported as currently reserved just because no worker ran. Polling does not extend deadlines. Payment, refund and shipment never consume/release these reservations in v1.

Pause/unpublish blocks NEW quotes/orders, not buyer history or release of held stock. Reads/cancels retain current member/order and tenant-retention boundaries; store lifecycle suspension must allow bounded release without authorizing new stock increases or metadata writes. Archived/deleted tenant handling must follow retained-order access policy, not silently orphan reservations; HO-1 tests the existing terminal lifecycle seam before activation. Cancellation/expiry committed first wins; no double decrement. Original deadline, terms and line snapshot remain immutable. Member revocation forbids member reads/replay, while trusted expiry still releases stock. No automatic cancellation notification or customer-contact side effect.

## Additive schema proposal — no SQL in HO-0

- Preserve `commerce_orders`, `commerce_order_lines`, `commerce_items` identities and source of truth. Add an explicit direct-reservation discriminator, real buyer relation, quote reference, reservation state/version/deadline/closure fields, and mapped tenant/instance constraints to the existing order authority; imported rows retain their original semantics and null direct-only fields.
- For direct lines, `transfer_id` may be null ONLY when the referenced order has this exact direct profile; imported lines still require their actual transfer. Concretely propose `commerce_orders.order_profile=imported_reseller|hosted_direct_reservation` with unique `(order_id,order_profile)`, matching `commerce_order_lines.order_profile` and composite FK; line CHECK requires direct transfer/acceptance/listing digest null and imported transfer non-null. Existing imported historical nullable acceptance fields stay valid. The discriminator cannot be changed after creation; HO-1 must add immutable/profile checks and adversarial SQL tests, not a nullable field alone. `acceptance_id/listing_sha256` remain null for direct sale; no acceptance or `commerce_transfers` row is fabricated. Direct orders are ineligible for all imported payment/payable/shipment code even if a hostile call reaches it.
- Existing legacy `buyer_payment` cannot stand in for direct reservation status. Add constraints ensuring direct rows remain payment-ineligible; neither `mode=test` on the display-only shop nor a fixture makes an operational reservation a simulated purchase or a paid order.
- Keep applied migration 134 immutable. The simplest additive evolution can retain its `accepting_orders=false/mode=test` safety check and add a separate explicit reservation setting/profile; hosted service credentials and old order paths remain prohibited. Do not globally drop the check to enable pending orders. No migration number/file/ledger row is added in HO-0. Provisional 138 may be assigned only after actual local 136/137 parents are integrated and main checked again.
- Register new buyer relation/quote fields and reverse-FK ownership in module-data DC-08, preserving DC-10 stock responsibility. PII is only the private member/order identity link already needed for authorization. Do not copy member profiles. Consumed quote/order/receipt retention needs a reviewed policy; no destructive TTL cleanup or promised export/delete in this slice.

## Verification and subsequent work

HO-0 tests strict DTOs, disabled financial assertions, arithmetic/expiry invariants and generated JSON structural parity. They do not prove authorization, stock effects or transactions. HO-1..3 require root review before DB/service/UI changes; no current route is registered here.

Required later evidence: seller A and distinct buyer B outside seller tenant; C, guild officer, same-community viewer and cross-instance grant denial; fresh-login same order; exact quote/intent retry after commit-response loss; two buyers race stock=1; all-lines rollback; price/publication/pause/stock-edit races; session expiry during receipt waits; quote expiry versus same-intent committed recovery; cancel/expiry/replay release once; expired read correct without cron; suspended store still releases stock; direct line cannot gain transfer/acceptance/payable; legacy imported two-payment/refund/shipment regression; restricted runtime roles and module-data detector coverage. Use barriers/DB clocks, not sleeps or fake provider events. No live purchase or payment evidence is implied.

No further business decision is required for this bounded direct-reservation slice. Delivery, tax, payment, real fulfilment, returns and external inventory remain unavailable and require their own subsequent scope rather than a guessed policy now.
