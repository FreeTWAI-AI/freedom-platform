# Same-database cross-store reservations (#437)

The candidate supports supplier A's one `commerce_items` balance being reserved through approved seller B/C selections. It is a reservation, not payment, fulfilment, a supplier payable, inventory export or remote inventory authority. Both the host admission flag and every participating shop's explicit owner setting must be enabled. Defaults remain OFF; migration 161 does not change existing settings.

## Contract and authority

New `freedom.hosted-shared-order-reservation/v1` quote/order schemas reuse the existing five-minute quote, thirty-minute reservation, bounded lines, immutable terms, stable buyer intent and disabled financial fields. Buyers opt in at `/hosted-stores/:slug/reservation-quotes` and `/reservation-orders`. `/me/reservations` and the owner's `/reservations` list/read/cancel routes accept retained direct and shared profiles. Original `/quotes`, `/orders`, `/me/hosted-orders` and owner `/orders` keep the direct-only contract. No registry release or old contract pin is rewritten.

Source resolution starts with seller-local SKU or the exact buyer's immutable quote. It verifies the same community/currency, both confirmed mappings for each source, current tenant/scope/owner/instance/deployment and installed store capability, explicit supplier admission, currently offered immutable version and exact accepted listing. Ordinary buyers may belong to another community; they gain no tenant membership. Private source drafts and buyer identities never become public DTOs. Transaction-local RLS switches are internal to this closed adapter and retain the actual buyer principal; the generic single-tenant binder is unchanged.

All participating tenant/instance lifecycle locks are sorted and taken **before** the existing community commerce lock. Current mappings/admission are checked again before receipt/projection completion. The existing order/item lock order and database/monotonic decision clocks remain. This intentionally retains community-level serialization; no throughput improvement or remote consistency is claimed.

Stock updates use server-resolved `(item_id, supplier_shop_id)` pairs, not buyer-supplied authority. Shared order lines persist the original item/shop/offer/acceptance/listing references. PostgreSQL checks quoted provenance, exact current consent and immutable order/line profiles. Imported-only financial foreign keys still reject hosted reservations. The same stock balance serves direct and cross-store orders; cancellation/physical expiry transitions once and releases the historical source even after withdrawal or suspension.

## Participant views and withdrawal

The current owner explicitly opens/stops admission through the versioned `/reservation-setting` command. The supplier `/supply-reservations` page has a signed owner/store-bound cursor and shows only that supplier's retained lines, agreed supply costs, seller name and reservation state. It does not return buyer identity/contact, buyer intent, quote digest, total cart value or other suppliers' lines. The supplier can observe physical expiry but cannot cancel another seller's unexpired order. Buyer and seller keep their existing cancellation authority and recovery guards when host admission is OFF.

Published storefronts remain immutable historical display snapshots. Withdrawal blocks new quote/submit and future publication immediately; it does not rewrite already published display content or accepted order terms. Member quote/submit reports unavailable supply. This slice does not add per-product live availability to the anonymous display. Existing orders remain readable/cancellable and expire against their original deadline; historical references do not grant continuing new-order authority.

## Release and recovery

Schema 160 → 161 preserves old direct orders and permits old direct readers/releases while no shared orders exist. **After the first shared reservation is written, recovery must retain the shared reader/release implementation.** Turning host admission OFF stops new reservations but does not erase shared orders, revert schema or make a pre-161 worker a complete recovery target. The existing release-compatibility checker records `commerce.hosted-shared-reservation.v1` in enabled/written/retained shape observations and requires that capability in every active/candidate reader. Host evidence must retain the floor after creation is disabled. Use a compatible reader build or forward fix; preserve existing schema-160 media/account reader floors and restore quarantine requirements.

Required evidence before activation: exact-head protected checks and independent review, schema upgrade with retained direct orders, restricted-role API counterexamples, A stock 10 with B/C concurrent 6+5, repeated cancel/expiry once, current consent/lifecycle refusals, party-specific order views, and ordinary-member browser operation. Local synthetic identities are engineering evidence. Controlled staging must separately exercise these paths and backup/restore against its actual source/schema; production admission requires its own recorded activation/acceptance. No payment or business-completion claim follows from a successful reservation.
