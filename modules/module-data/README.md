# Module data

This module owns the tenant data-responsibility catalog and the checker that compares it with an installed schema. It does not expose an HTTP route, and it does not delete, export, or restore tenant rows.

`catalog.ts` freezes catalog version `1` for the datasets tenant data touches today: DC-04, DC-06, DC-08, DC-13 and DC-14. DC-04 also registers `tenant_high_risk_verifications`, `tenant_ownership_transfers` and `tenant_recovery_cases`. `tenant_authority_policies` and `platform_admin_tenant_recovery_capabilities` have no tenant column and stay without row security. `catalog-check.ts` reads `pg_catalog` and reports a sorted finding when a tenant-bearing table, column, policy, asset purpose, or unbounded retention string is missing or stale. Retention stays `policy_undecided` until OPEN-07 (and OPEN-05 for receipt windows) names a duration. Row security is enabled without `FORCE` (OPEN-14).

The snapshot retains foreign-key edges and each table's direct-column, tenant-scope CHECK and asset-purpose evidence. Tenant-scope evidence requires at least one CHECK referencing `scope_kind` and every such CHECK on the table to admit tenant; `IS NULL` / `IS NOT NULL` on a bound column are evaluated, while unsupported forms still count as admitting. Every existing catalogued table is checked even if it leaves the detected set. A declared resolution must match that live evidence; each `fk_chain` hop must exist and end at a table with its own tenant evidence.

Finding codes: `unregistered_table`, `unregistered_column`, `stale_location`, `stale_column`, `rls_mismatch`, `policy_mismatch`, `force_rls_set`, `unregistered_asset_purpose`, `tenant_resolution_mismatch`, `retention_unbounded`. `tenant_resolution_mismatch` names the table whose declared resolution no longer matches the installed schema.

DC-08 also covers the existing `commerce_shops`, `commerce_items` and `commerce_selections` used by hosted stores. These tables have no tenant column: a shop resolves through the reverse `commerce_resource_tenants.resource_id -> commerce_shops.shop_id` FK; items and selections first follow their own `shop_id` FK. The snapshot records ordered source/target column pairs, and `fk_path` verifies each directed hop and independent tenant evidence at its endpoint. The three explicit commerce paths are detector seeds independent of catalog entries, so removing an entry fails coverage. They do not reverse arbitrary FKs or expand into credentials, legacy orders, transaction participants or shared parents. Other mapping families need their own reviewed coverage rules.

This is schema coverage, not a row reader or export allowlist. Hosted readers still require `resource_kind=shop`, `mapping_state=confirmed`, the bound tenant/instance and current capabilities; selection ownership does not authorize another supplier's item. Imported/unmapped or ambiguous resources are not assigned by member identity. The existing shared commerce tables remain exempt from RLS; the mapping table retains its existing tenant RLS. Items are declared once in DC-08 for hosted source coverage, retaining DC-07 product/offer and DC-10 stock/reserved responsibility. No export, import, restore or external migration capability is implemented or accepted by this change.
